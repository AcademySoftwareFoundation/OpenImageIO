# Tasks: Image Format Security & Stability Audit

**Input**: Design documents from `specs/002-format-security-audit/`

**Prerequisites**: plan.md, spec.md, research.md, data-model.md, contracts/

**Tests**: Test tasks ARE included — the spec makes malformed-input regression
coverage and sanitizer-clean fuzzing a hard requirement (FR-010, SC-001, SC-005;
constitution Principle V). They are per-format, not TDD-first.

**Organization**: The natural unit of audit work is ONE FORMAT (spec FR-011,
US2). Note: the delivery packaging was later amended (see FR-011) — the
near-identical check_open / check_compression_ratio guards and the simple
integer-overflow fixes are batched into shared cross-format commits, while
extensive per-format hardening stays its own commit; the per-format audit scope
is unchanged. The three user stories are cross-cutting and are satisfied
*inside every format phase*:

- **US1 (P1)** — hostile input can't crash/corrupt memory → the hardening tasks
- **US3 (P3)** — safe `valid_file` detector → the valid_file task
- **US2 (P2)** — isolated, reviewable per-format PR → the verify+deliver task

So each format phase's tasks are labeled by the story they serve. Phases are
ordered by risk × prevalence (research.md Decision 8).

## Format: `[ID] [P?] [Story] Description`

- **[P]**: Can run in parallel (different files/formats, no dependency on incomplete tasks)
- **[Story]**: US1 / US2 / US3
- Every task names a concrete path. Reader TU is `src/<fmt>.imageio/<fmt>input.cpp`
  (exact basename varies, e.g. `exrinput.cpp`); the plugin directory is authoritative.

## The Standard Per-Format Task Set (reference)

Each format phase instantiates these five steps against its own plugin
(see `contracts/per-format-audit.md` and `contracts/reader-hardening-api.md`):

- **A [US1]** Census + open-time guards: add `check_open(spec, ROI)` with format-spec
  extents, `check_compression_ratio(spec, filesize)`, reject non-positive
  width/height/channels/depth/bit-depth, promote all size/offset math to 64-bit
  (`imagesize_t`/`int64_t`).
- **B [US1]** Decode-path safety: validate every declared region/offset/seek against
  the actual byte count; check every underlying-library return/error with error-path
  cleanup (no leaks); wire failure posture (`imageinput:strict` → metadata-only
  defects; ALWAYS hard-error pixel defects); migrate pointer+length buffers to
  `span`/`cspan` + `valid_raw_span_size()`.
- **C [US3]** Audit/repair `valid_file()` for correctness and bounds-safety.
- **D [US1]** Add malformed-input fixtures per hazard class H1–H9 under
  `testsuite/<fmt>/`. The fuzzer seeds from these automatically once the
  format's fixture dir is listed in `FORMAT_SOURCES`
  (`src/fuzz/populate_corpora.py`); do NOT duplicate fixtures into
  `src/fuzz/corpora/<fmt>/`, which now holds only synthetic seeds that have no
  testsuite home (see `docs/dev/fuzzing.md`).
- **E [US2]** Verify (ASan+UBSan clean on corpus, testsuite green, valid files
  byte-identical) → fix obvious shared-hazard writer bug on the read→write path OR
  log it to the deferral doc → open scoped PR with the C1–C10 findings summary →
  update the data-model.md inventory status. Do NOT edit `CHANGES.md` — it is
  filled in at release time; editing the in-development section makes the patch
  conflict when backported to release branches that lack that section.

### exif (`src/libOpenImageIO/exif.cpp` — decode_exif, reached from jpeg/png/tiff)
- [x] T144 [US1] Census + harden `decode_exif`/IFD walk: bounds-check every TIFF-directory offset/count against the blob size; guard recursive/self-referential IFD offsets (H9); 64-bit offset math. Known P0 short-blob/recursive OOB in the deferral log is the anchor case. — DONE. The two cases from the external GHSA draft were already closed before this task ran: the short-blob `TIFFHeader` overread by `check_open`-era work (`exif.size() < sizeof(TIFFHeader)` at the top of `decode_exif`), and the recursive `ndirs` overread by 7b111b1c0 on this branch. The census found **three more, two of them crashes on an ordinary Release build with no sanitizer**. (1) **`tiff_data_size()` reports an unrecognized TIFF data type as `size_t(-1)`, and `dataspan()`/`dataptr()`/`tiff_dir_data()` multiplied that sentinel by the entry's count and fed it to the bounds arithmetic.** `size_t(offset) + size_t(-1)` wraps to `offset - 1`, which passes any `> buffer size` test, so the helper returned a span of length `size_t(-1)` pointing into the blob. The trigger is not exotic: `EXIF_UTF8_TYPE = 129` is the Exif 3.0 UTF-8 string type that OIIO added in #4961 and that `add_exif_item_to_spec` explicitly accepts, but `tiff_data_size` was never taught about it, so *every* Exif 3.0 UTF-8 tag took this path. A 26-byte blob (one tag, type 129, count 1, offset 1) gives a heap OOB read under ASan and an **uncaught `std::length_error` that aborts the process** on a Release build, from `std::string(dspan.begin(), dspan.end())`. Fixed at both levels: `tiff_data_size` now returns 1 for `EXIF_UTF8_TYPE` (which also makes Exif 3.0 UTF-8 tags decode correctly for the first time, rather than being silently dropped or crashing), and a new `pvt::dirdata_size()` rejects the sentinel so no other unknown type can wrap the arithmetic. The offset math in `dataptr`/`dataspan` is promoted to `int64_t` while there (`td.tdir_offset + offset_adjustment` was `uint32 + int` assigned to `int`, relying on wrap plus a `< 0` test). (2) **Unbounded IFD recursion depth.** `ifd_offsets_seen` prevents *cycles* but not *depth*: each nested IFD only has to sit at a new offset, and 18 bytes buys one level, so a blob can chain as many levels as its own length allows. Measured: a 180 KB blob (10,000 levels) exhausts the stack. JPEG APP1 caps a blob at 64 KB, but PNG `eXIf` carries a 31-bit length and HEIF/PSD are unbounded. Capped at 32 levels (real files nest two or three) via a thread-local counter in `read_exif_tag` — a parameter would not do, because the MakerNote handler that re-enters the walk goes through `TagInfo::handler`, whose signature is fixed and public. A 9 MB, 500,000-level blob now decodes cleanly. (3) **`OIIO_ALLOCA` with a file-controlled count** in the RATIONAL/SRATIONAL branches of `add_exif_item_to_spec`. `OIIO_ALLOCA`'s own `assert(size < (1<<20))` is a plain `assert`, compiled out under `NDEBUG`, so a Release build has no check at all: a 32 MB Exif blob holding one RATIONAL tag of count 4,000,000 alloca's 16 MB and **SIGSEGVs** (verified against the release library). Replaced with `OIIO_ALLOCATE_STACK_OR_HEAP`, OIIO's existing small-on-stack/large-on-heap idiom. Note this is much worse off the main thread — a worker with a 512 KB stack falls over at a 1 MB blob. Also fixed: the entry-bounds test in `read_exif_tag` used `dirp + sizeof(TIFFDirEntry) >= buf.end()`, an off-by-one that discarded a legitimate final directory entry ending exactly at the blob end; and `decode_exif` read the `TIFFHeader` through a cast that assumed alignment, now a memcpy. C4/C5/C7 outcomes recorded above; C1/C2 N/A (no image dimensions or allocation-from-header in a metadata decoder); C3 N/A (no `valid_file`); C10 N/A (`encode_exif` builds from in-memory attributes, not from file bytes).
- [x] T145 [US1] Malformed fixtures + fuzz seeds (short blob, truncated IFD, recursive offset) exercising all three container routes; verify ASan/UBSan clean; deferral triage. — DONE. Four fixtures, two containers, both built by committed generators: `testsuite/jpeg-corrupt/src/make-exif-fixtures.py` writes `corrupt-exif-utf8-type.jpg` (370 B) and `corrupt-exif-deep-ifds.jpg` (2.1 KB), and `testsuite/png-damaged/src/make-exif-fixtures.py` writes the same two payloads through a PNG `eXIf` chunk. ### xmp (`src/libOpenImageIO/xmp.cpp` — decode_xmp)
- [x] T146 [US1] Census + harden XMP parse: bounds/loop safety on malformed or oversized XML packets; check all return paths. — DONE. The census found **three defects, one of them a crash on an ordinary Release build**, all of them loop/recursion bounds rather than buffer bounds: pugixml owns the byte-level parsing and it is solid (confirmed separately -- a 75 MB packet nested 5,000,000 levels deep parses in 78 ms with no recursion, because its parser is a cursor loop and its destructor frees a pool), so the whole hazard surface is what `decode_xmp_node()` does with the resulting tree. (1) **Unbounded recursion.** `decode_xmp_node()` recursed once per level of XML nesting and its `level` parameter was incremented but never read. A 2.5 KB PNG carrying 100,000 `<foo:a>` elements in a deflated `zTXt` chunk **SIGSEGVs a plain Release `oiiotool`**; ASan reports `stack-overflow` at 5,000 levels, and a 64 KB JPEG APP1 marker (~9,000 levels) is already enough to take down a sanitizer build or any worker thread with a small stack. Capped at 64 levels -- real XMP nests about five. (2) **Quadratic list accumulation, with permanent memory.** For each item of an `IsList`/`IsSeq` attribute, `add_attrib()` re-read the existing attribute, `splitsv`'d it, appended, re-`join`ed, and wrote the whole thing back via `spec.attribute()`, which interns a **ustring** -- so every intermediate value of a growing list is retained for the life of the process. Measured: a 51.6 KB PNG (20,000 `dc:subject` items) took 11.6 s and 3.2 GB RSS; 1.1 MB of XMP took 22.9 s and **11.2 GB**. The existing `if (isList && totalsize > 64*1024) break;` guard never fired here, because `isList` is only true one level below an `rdf:Bag`/`Seq`/`Alt`/`li`, and these items are siblings under `rdf:Description`. (3) **Quadratic attribute insertion.** `ImageSpec::attribute()` is a linear scan, so a packet full of distinct attribute names is quadratic in their count: 1.26 MB of XMP -> 12.2 s. Fixed (2) and (3) together with an `XMPbudget` threaded through the recursion, capping one `decode_xmp()` call at 4096 attributes and 1 MB of accumulated attribute payload; because `add_attrib()` returns the size of the *whole* re-joined list on each append, that byte total is exactly the quadratic quantity, so capping it caps the blowup directly. `mylist` (the semicolon accumulator, unbounded when the parent is not a list node) is capped too. Post-fix, every case above is under 30 ms at baseline RSS. **C10 APPLIED**: unlike `encode_exif`, `encode_xmp` is not N/A -- it interpolates attribute values into XML text with no escaping, and those values may have come from `decode_xmp` reading a hostile file. Verified: an `IPTC:City` of `evil" xmp:Rating="5` was written out as a closed attribute plus a real injected `xmp:Rating` attribute, and `a<b>c&d` produced malformed XML; values are now XML-escaped and round-trip exactly. C1/C2/C3 N/A (a metadata decoder has no image dimensions, no allocation sized from a header, and no `valid_file`); C4/C6/C7 N/A (the input is a `string_view`/`cspan` throughout, with no offset arithmetic and no raw `ptr,len` hand-off); C5 already-satisfied (the pugixml parse result is checked, and deliberately tolerated -- minor malformations are common in real files, per the existing comment). C8 is unchanged: `decode_xmp()` returns `true` on every path, so the caps truncate silently and PSD's `if (!decode_xmp(...))` error branch stays dead -- changing that is a posture change across five containers, logged as a deferral rather than decided here.

### icc (`src/libOpenImageIO/icc.cpp` — decode_icc_profile)
- [x] T148 [US1] Census + harden ICC parse: tag-table offset/size bounds against the profile length; 64-bit math; reject profiles whose declared length exceeds the buffer. — DONE. The census confirmed the **OOB surface was already closed**: `decode_icc_profile` rejects a header shorter than 128 bytes, requires `profile_size == iccdata.size()` exactly (so a declared length that over- *or* under-states the buffer is refused, not just "exceeds"), and every tag/`mluc`-string range is checked before it is read. What it did **not** do was get there safely. Three latent UB defects, all reachable from an ordinary metadata blob: **(1) out-of-bounds pointer formation.** The range checks were written as `check_span(iccdata, iccdata.data() + tag.offset, max(4,tag.size))` and `... + tag.offset + stroffset`, i.e. the code formed `base + offset` *first* (with `offset`/`stroffset` file-controlled uint32s) and only then compared — forming a pointer more than one-past-the-end is UB in C++ and, on a 32-bit build, the `uint32 + uint32` pointer math can wrap and make an OOB tag *pass* the check. Replaced with a new `range_in_bounds(offset, len, size)` helper that does the comparison in `uint64_t` and never constructs the pointer until the range is known good. **(2) misaligned loads (the headline finding).** Every scalar was read with a `*(const T*)(ptr + offset)` cast — the header, `tag_count`, each 12-byte `ICCTag`, and inside `mluc` the `nrecords`/`recordsize`/`language`/`country`/`len`/`stroffset` fields — at offsets taken verbatim from the file. The ICC spec aligns tag data to 4 bytes, but a corrupt/hostile profile need not: a tag whose data lands on an odd offset makes `extract<uint32_t>`/`extract<uint16_t>` do a misaligned load. **(3)** the `mluc` UTF-16 value was copied via `std::u16string((const char16_t*)start, len/2)`, a misaligned 2-byte-element read when `stroffset` is odd. A single hand-built `mluc` at an odd offset trips **all three** UBSan sites at once (`icc.cpp:210` for the uint32 and uint16 reads, and the libc++ `char_traits::copy` for the char16_t read) — verified by reverting the fix on the `address,undefined` build. Fixed by routing **all** reads through `memcpy` (header, `extract<T>`, the `ICCTag` specialization, and the UTF-16 copy) and promoting the bounds math to 64 bits; the byte values read are identical, so valid profiles are unchanged. C-checklist: **C1/C2/C3 N/A** (metadata decoder — no dimensions, no header-driven allocation, no `valid_file`); **C4 APPLIED** (64-bit `range_in_bounds`, no OOB pointer formation); **C5 N/A** (hand-rolled, no underlying library call); **C6** input is already `cspan<uint8_t>`, internal reads now `memcpy` rather than raw casts; **C7 already-satisfied** (`profile_size` exact-match + every tag/string range validated `≤ size`); **C8 already-satisfied at all callers** — jpeg, png, tiff, webp, jpeg2000, and psd each gate a `decode_icc_profile` failure behind `imageinput:strict` (metadata-only posture: tolerated by default, hard error under strict); **C9 APPLIED** (the alignment fixes); **C10 N/A** (writers embed the raw ICC blob verbatim; no reader-derived offset feeds the writer). No deferrals.

Two fixtures built by a committed generator, `testsuite/jpeg-corrupt/src/make-icc-fixtures.py`, each a valid 1x1 JPEG with a hand-assembled APP2 `ICC_PROFILE` segment prepended (the generator embeds its own stripped base JPEG, so the fixtures depend on no writer and carry no version-dependent metadata): `corrupt-icc-unaligned-mluc.jpg` (529 B) places an `mluc` tag at an odd offset with its English UTF-16 string at a second odd offset — the direct repro for defect (2)/(3), and *not* a rejection case: it is a well-formed profile that must decode, and post-fix it yields `ICCProfile:profile_description = "Hi"` while pre-fix it fired the three UBSan alignment errors; `corrupt-icc-oversized.jpg` (484 B) declares `profile_size = 0x7FFFFFFF` behind ~132 actual bytes and must be rejected on the size-mismatch check with a bounded read (the "oversized length" case; "tags past end" is already covered by the pre-existing `corrupt-icc-4551.jpg`). ## Dependencies & Execution Order

### Phase Dependencies

- **Setup (Phase 1)**: no dependencies — start immediately.
- **Foundational (Phase 2)**: depends on Setup — BLOCKS all format phases.
- **Format phases (Phases 3–7)**: each depends only on Foundational. Formats are

- C (valid_file) is independent of A/B → marked [P].
- D (fixtures/seeds) after A+B+C so the corpus exercises the new guards.
- E (verify + PR) last — it is the gate that closes the format.

- Setup tasks T002/T003/T004 run in parallel.
- Foundational T007/T008 run in parallel after T005/T006.

- Within a format, the C (valid_file) task is [P] against A/B; the first task of the
